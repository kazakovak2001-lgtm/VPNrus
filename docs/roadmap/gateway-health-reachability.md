## Notes

`TransportHealth` (Phase 2A) is a real typed model (`UNKNOWN`/`HEALTHY`/`DEGRADED`/`UNREACHABLE`/`NOT_IMPLEMENTED`), now populated with real, transport-level evidence: `TransportHealthCalculator` (B8L1) derives it from `ConnectionOutcomeStore`'s real per-attempt history. `SmartConnectDecisionEngine.decideAuto` (Manual-gateway-mode's own transport picker) still doesn't act on `health` (see Smart Connect row above). **B19 (2026-09-01) update: for AUTOMATIC gateway selection specifically, health/reachability ARE genuinely decision-driving** - `AutoGatewaySelector` (reusing `PathScorer`/`ReachabilityEngine` verbatim, never a parallel scorer - see that row's own docs) has ranked candidates by real `TransportHealth`/`EndpointReachability`/local history/capability maturity since B16; B19 adds a real, unit-proven demonstration (`AutoGatewaySelectorTest`'s "fresh AWG UNREACHABLE plus REALITY REACHABLE ranks REALITY first" / "AWG DEGRADED plus REALITY HEALTHY reorders past static preference" / "all UNKNOWN falls back to static preference" cases) that this reordering genuinely happens end to end, not merely at the `PathScorer` unit level. B11 adds the genuinely PER-ENDPOINT counterpart this row used to lack - see Endpoint / Path Reachability Fabric below, kept as its own row rather than merged into this one because `EndpointReachability` answers a materially different question than `TransportHealth` (this endpoint, this transport, this network - vs this transport in general). B12 further splits per-endpoint evidence itself: `ReachabilityEvidenceSummary.controlPlaneReachable` (the gateway's HTTPS API - manifest/activation/provisioning) is now a field DISTINCT from `endpointSpecificReachable` (a real data-plane attempt outcome for that exact endpoint+transport, now derived from `ConnectionOutcomeStore`'s own per-attempt `gatewayId`/`transport` fields rather than reusing the control-plane probe for both) - the task's own "do not collapse control-plane/endpoint/transport signals" requirement, unchanged and still honored by B19's own additions (neither the new diversity fix nor the new cooldown penalty ever reads or writes `controlPlaneReachable`). **B13** - this evidence is now actually surfaced in the debug diagnostics UI (`AppRoot.reachabilityDiagnosticsLines`, `DiagnosticsDialog`): manifest version/source/expiry, per-endpoint id/roles/region/provider/ASN/transports, per-(endpoint,transport) reachability state with control-plane and endpoint-specific evidence and their independent ages, and ranked `PathCandidate`s with type/eligibility/score/reasons - built generically by iterating `ReachabilityDiagnosticsSnapshot`'s own lists, so it already renders N endpoints correctly even though only one real one exists today. **B19** - the live Auto-mode diagnostics line (`AppRoot`'s `autoCandidatesLine`) now also surfaces each ranked candidate's typed reason tokens (`PathScorer.Reason` - `ENDPOINT_REACHABLE`/`TRANSPORT_HEALTHY`/`FAILURE_COOLDOWN`/`DIVERSITY_BONUS`/etc, task requirement 14's own vocabulary), not just gateway/transport/score. No secret/credential field is ever included (the underlying types structurally carry none). **Physically validated end to end (2026-09-01) - promoted to IMPLEMENTED for Automatic gateway selection.** On the real physical test device, in real Auto mode with transport preference genuinely `Auto` (never pinned): (A) baseline - the live Diagnostics `Auto candidates (ranked)` line showed `GERMANY/AMNEZIA_WG(score=2029973,ENDPOINT_UNKNOWN,TRANSPORT_HEALTHY)` ranked first; connecting normally produced `Current transport: AMNEZIA_WG`/`Gateway: Germany / Frankfurt` with a real 623ms handshake - the executed attempt matched candidate #1 exactly. (B) controlled dynamic reordering - two REAL `FAILURE` outcomes for Frankfurt AWG were written into `ConnectionOutcomeStore`/`FilePathHistoryStore` via a genuinely minimal debug-only mechanism (`MainViewModel.debugRecordConnectionFailure`, one more button in the existing `isDebugBuild`-gated Diagnostics dialog - writes through the EXACT SAME stores/write path a real failed connection attempt already uses, never a fake/parallel evidence channel; no server config, no AWG peer config, no provisioning identity touched). The NEXT freshly-built Auto plan showed `GERMANY/AMNEZIA_WG(score=-1080,ENDPOINT_UNREACHABLE,TRANSPORT_UNREACHABLE,RECENT_FAILURE_THIS_NETWORK,FAILURE_COOLDOWN)` demoted to LAST place, with `GERMANY/XRAY_REALITY(score=2020000,...)` now ranked FIRST; connecting produced `Current transport: XRAY_REALITY`/`Gateway: Germany / Frankfurt`, `Protected` - the executed attempt again matched the new candidate #1 exactly, with no `AwgXrayFailoverPolicy`/manual-picker involvement (transport preference stayed `Auto` throughout - the reordering came entirely from ranking evidence, not a fallback policy). Manual-gateway-mode's own transport picker remains untouched/static (see Smart Connect row) - this promotion applies to Automatic gateway selection specifically, never claimed for Manual mode. **B19-3 (2026-09-01) eligibility clarification**: a candidate with FRESH endpoint-specific `ReachabilityState.UNREACHABLE`, or `TransportHealthState.NOT_IMPLEMENTED`, is now genuinely INELIGIBLE (`PathScoreResult.eligible = false`) rather than merely low-scored-but-still-executable - `AutoGatewaySelector` already only ever promotes `eligible == true` results into the executable plan, so this closes a real gap where a confirmed-dead path could still occupy a `MAX_ATTEMPTS` slot. Transport-wide `UNREACHABLE` is ineligible UNLESS a fresh, stronger, endpoint-specific `REACHABLE` read overrides it - the one explicit precedence rule `PathScorer.isEligible`/`ineligibilityReason` enforces, never duplicated elsewhere. `DEGRADED`/`UNKNOWN` remain eligible, and stale evidence still decays to `UNKNOWN` (hence eligible again) entirely within `ReachabilityEngine` - `PathScorer` has no second freshness check. `PathScorerTest`'s own eligibility cases (fresh UNREACHABLE ineligible regardless of health; endpoint REACHABLE overriding transport-wide UNREACHABLE; endpoint UNKNOWN with transport-wide UNREACHABLE staying ineligible; DEGRADED/UNKNOWN eligible; NOT_IMPLEMENTED ineligible; stale-decayed UNREACHABLE eligible via a real `ReachabilityEngine.assess` call) and `AutoGatewaySelectorTest`'s own proof (a fresh-UNREACHABLE AWG candidate is entirely ABSENT from the plan and `nextCandidate` never returns it) cover this directly. Full suite (886 tests) passes; not re-validated physically this pass (no ranking-order/execution-path behavior changed for any ALREADY-eligible candidate - only genuinely-dead candidates are now excluded outright instead of merely last-ranked, and the existing physical pass already proved that ranking order drives real execution).
