The bounded, per-device, zero-touch enrollment service closed PR #58 built (`gateway/api/field_enrollment.py`, `gateway/tools/field_enrollment_admin.py`, Android `FieldCredentialStore`/`FieldCredentialStoreFactory`/`FieldEnrollmentResult`, `ProvisioningClient.fieldEnroll`, `MainViewModel.ensureZeroTouchEnrollment`) was ported onto CURRENT `main` (post-B67.2/B67.3) rather than merged as-is - PR #58 itself stays closed/unmerged/untouched. Server-side reuses the SAME `activations.py` entitlement/binding/provisioning primitives `/v1/activate` already uses (`register_credential`/`provision_with_activation`) - no second authorization system; the credential is genuinely RANDOM (`secrets.token_urlsafe`, 256 bits), never HMAC/secret-derived (that earlier design was already replaced before PR #58 closed - not resurrected here). Bounded per-device cap + race-free atomic idempotent reservation (`FieldEnrollmentIndex`) + two-level rate limiting (per-public-key and global, the latter defending against an attacker minting fresh public keys) + rollback-on-provision-failure (a failed attempt releases its reserved slot). Fixed with a fixed-size, 64-slot shard pool (`SHA-256(public_key) % 64`, `_key_lock_shard_index`/`_key_lock_file_path`) - the persistent footprint is now bounded by that constant regardless of request volume; a shard collision between two different keys only ever serializes their attempts against each other, never corrupts correctness (every read/write inside the locked section is still keyed by the real public key/credential digest); no inode-replacement bypass is possible since a shard's lock file, once created, is never unlinked/replaced for the deployment's lifetime.
