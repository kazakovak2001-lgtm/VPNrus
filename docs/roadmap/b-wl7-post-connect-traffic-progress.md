A pure `TrafficProgressMonitor.evaluate()` judges `VERIFIED`/`STALLED_AFTER_INITIAL_PAYLOAD`/`NO_PAYLOAD`/`IDLE`/`UNAVAILABLE`/`VERIFYING` from bounded time windows over the EXISTING, already-present `TransportStats.Counters` type - never a byte-count threshold (a 1-byte and a 1,000,000-byte payload take the identical code path once the window logic is satisfied). **Live wiring (current pass)**: `VpnController.launchLiveProgressObservation`, called once right after a real fresh AmneziaWG handshake, samples the active transport's real `stats()` at the SAME poll cadence `awaitFreshHandshake` already uses (no second polling cadence, no new coroutine framework), feeds the accumulated samples to `TrafficProgressMonitor.evaluate` after every poll, and stops the instant a decisive verdict is reached or the bounded `verificationWindowMillis + stallWindowMillis` window elapses - so it always terminates, never loops indefinitely, and is never a second watchdog. It writes exactly ONE `TransportAttemptObservation` per attempt (never per-poll, never a duplicate across reconnect backoff), is cancelled the instant a newer attempt/disconnect supersedes it (same generation-ownership lock `reconnectJob` already uses), never calls `disconnect()`/`startReconnect()`/`setState()`, and B33's existing post-Connected confirmation (`XrayCoreController.confirmRemoteConnectivity`, the relay-health watchdog) remains the sole live connection-health/reconnect authority, completely unmodified. A transport whose `stats()` never reports real counters (every non-AmneziaWG kind today) is recorded honestly as `NOT_OBSERVED`, never a fabricated claim. This is what makes `POSSIBLE_EARLY_DROP`/payload-aware `POSSIBLE_UDP_FILTERING` reachable from real AmneziaWG production traffic (see B-WL1's row) - still gated entirely behind physical-network validation, which does not exist yet for any restricted/Russia network.
