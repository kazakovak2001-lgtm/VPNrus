## Capability

Resilient Activation & Control-Plane Access

## Status

**FOUNDATION** (B30, 2026-09-03)

## Notes

Makes activation/profile-retrieval network calls bounded, typed, and origin-list-driven, without a second trust system. **Trusted origin model**: `ControlPlaneOrigin(gatewayId, host)`, built ONLY by `ControlPlaneOriginSetBuilder.forGateway(gatewayId)` from `ProductionGatewayCatalog` (the same compiled trusted gateway facts everything else in this codebase already uses) - never a caller-suppliable URL. Today's catalog carries one physical origin per gateway; the list shape is what makes the mechanism genuinely N-origin-capable the moment a second trusted origin exists, no call-site changes needed then. **Generic executor**: `TrustedOriginRequestExecutor` (pure, synchronous, no I/O) tries each origin at most once, in order, bounded by `origins.size` - never unbounded, stops early on `AUTHORIZATION_REJECTED` (a rejected credential is never retried against a different origin). Reused by `ActivationResilienceCoordinator` (activation) and `IngressProfileProvisioner` (ingress-profile diagnostics), never transport-specific copies. **Failure taxonomy**: `ControlPlaneFailureReason` (DNS/timeout/TLS/HTTP-unavailable/authorization-rejected/malformed/trust-rejected/untrusted-redirect/all-origins-exhausted), mapped into eight new `DiagnosticFailureReason.CONTROL_PLANE_*` values for B29's support bundle. **Redirect lock-down**: `ProvisioningClient.executeGeneric` (shared by all five endpoints - peers/activate/xray-profile/xray-tls-profile/ingress-profile) now sets `instanceFollowRedirects = false` - a real audit finding: `HttpsURLConnection` followed redirects transparently by default, before any status-code check ran, which would have silently resent the bearer credential to whatever host a response named. **Activation resilience**: `ActivationResilienceCoordinator` wraps `ProvisioningClient.activate` with the executor's bounded/typed discipline, skips the network via a caller-supplied `hasValidLocalActivation` check, and is idempotent by construction (never rotates identity - the caller's already-get-or-created public key is always reused, matching the server's own credential-digest-locked idempotent activation in `gateway/api/activations.py`) - never applies/persists anything itself. **PR #44 review fix**: `MainViewModel.activateDevice`'s real network call now genuinely routes through `ActivationResilienceCoordinator` via a new `controlPlaneOriginsForActivation` constructor seam (defaults to the real `ControlPlaneOriginSetBuilder::forGateway`) - the ~250-line success/persistence block (gateway-identity cross-check, config/profile/identity writes, Xray/TLS provisioning) is untouched, now fed whichever origin's result actually succeeded; `retryActivation()` already called `activateDevice` verbatim so Retry automatically reuses the resilient path. **Trusted-origin audit performed**: decoded the embedded signed manifest directly - each gateway's endpoint carries exactly one host across all transport bindings (different ports/protocols, not alternate hosts); audited `gateway/api/activations.py` - activation state is a per-VPS-local store, Germany and Stockholm are confirmed NOT interchangeable activation backends. Conclusion: no genuine second trusted control-plane origin exists today for either gateway - `ControlPlaneOriginSetBuilder` was left unchanged rather than inventing one, per the review's own accepted "report the architecture blocker" alternative; the fallback mechanism itself is proven correct through the real `activateDevice()` path via the new test seam, injecting a synthetic two-origin list. **Xray/TLS profile fetch now also genuinely wired through the executor** (`XrayProfileProvisioner`/`XrayTlsProfileProvisioner` gained additive nullable `gatewayId`/`diagnosticsRecorder` params, wired for all four Factory instances) via a new `fetchThroughTrustedOrigins` helper; `IngressProfileProvisioner` deliberately stays diagnostics-instrumented only (it's `EndpointId`-scoped, not `ProductionGatewayId`-scoped, so the same origin model would misrepresent its trust). **New tests**: `TrustedOriginProfileFetchTest`, `MainViewModelActivationGatewayIdentityTest` additions (primary-fails/secondary-succeeds applied+persisted through the real flow, malformed-primary-leaves-no-partial-state, all-origins-exhausted friendly failure, authorization-rejection stops fallback), `MainViewModelSupportDiagnosticsTest` addition (real activateDevice diagnostics carry no host/IP/URL/credential). All new + full existing suite green (1190 total, same one pre-existing unrelated `EffectiveConfigDiffTest` failure); `compileDebugKotlin`/`testDebugUnitTest`/`assembleDebug` all re-verified green. **PR #44 review fix, round 2 (origin-discarding blocker)**: every gateway-scoped network seam is now genuinely origin-aware - `activationClient`/`stockholmActivationClient` and `XrayProfileProvisioner`/`XrayTlsProfileProvisioner`'s `fetchXrayProfile`/`fetchXrayTlsProfile` all changed from `(publicKey, credential) -> Result` to `(origin, publicKey, credential) -> Result`, each defaulting to `{ origin, pk, cred -> ProvisioningClient.xxx(pk, cred, origin.host) }` - round 1's wiring wrapped the calls in the executor structurally but every actual callback still discarded `origin` and re-dialed the SAME pre-bound host, so a 2-origin executor was retrying, not failing over. `XrayProfileProvisioner`/`XrayTlsProfileProvisioner`'s `gatewayId` is now non-null (defaults to GERMANY) so `provision()` always routes through the origin-aware path, no parallel non-origin-aware branch. New tests prove HOST-LEVEL routing directly (not just call count): `MainViewModelActivationGatewayIdentityTest` uses real distinct hostnames (`"primary.example"`/`"secondary.example"`) and asserts the exact sequence of hosts the fake network function was actually called with. All new + full existing suite green (1190 total, same one pre-existing unrelated failure); `compileDebugKotlin`/`testDebugUnitTest`/`assembleDebug` re-verified green. **Still not done**: real production data has only one physical origin per gateway (see audit above) so cross-HOST fallback isn't exercised by live traffic yet, only proven via the test seam; no live-HTTPS integration test for the redirect lock-down; this does NOT prove Russia hard-whitelist bypass, which remains UNVERIFIED.
