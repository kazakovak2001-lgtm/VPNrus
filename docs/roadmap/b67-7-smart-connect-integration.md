## Column 3

Technical integration of B67.6's entitlement-derived gateway eligibility into the EXISTING `AutoGatewaySelector`/`TransportOrchestrator` candidate pipeline - never a parallel connect path, never a second selector. Traced the REAL runtime (not just `PROJECT_ARCHITECTURE.md`'s prose): `MainViewModel.connectAuto()` actually reads candidates from `buildCombinedAutoRankingSnapshot()`, not the separate, purely-observational `buildAutoGatewayCandidates()`/`autoGatewayCandidates()` - both now read trusted-manifest endpoints through one new shared private helper, `currentEligibilityFilteredManifestEndpoints()`, so the constraint applies identically to whichever pipeline is actually driving a connection, never only to the diagnostics-only one. `net.pocvpn.client.activation.EntitlementGatewayEligibility.filterEligibleEndpoints` (pure function, no I/O) is the "trusted candidates + eligibility constraint -> eligible trusted candidates" step - a `null` constraint returns the input unchanged (byte-for-byte pre-B67.7 behavior); a non-null `Set<ProductionGatewayId>` keeps only endpoints that map to it via the EXISTING `ProductionGatewayCatalog.byEndpointId` (never a second catalog), and deliberately leaves any endpoint that maps to NO product gateway (an ingress/exit-only manifest entry) completely untouched - B67.6 eligibility has no defined meaning for a non-gateway role, so the relayed/ingress candidate space (`mergedIngressAwareEndpoints`) stays outside this constraint's reach by construction. **The one architecture decision this slice made explicitly** (audited for staleness rather than guessed): a new session-scoped, in-memory-only `MainViewModel.currentEntitlementEligibleGatewayIds: Set<ProductionGatewayId>?` field holds the current constraint - `null` (no constraint) until set, NEVER persisted, so a process restart always restores the unconstrained pre-B67.7 candidate list, mirroring `ActivationPackageRedeemer`'s own "pending state is never persisted, restart requires re-import" discipline exactly. It is set ONLY after `activateDeviceAwaiting` reports a genuinely SUCCEEDED outcome for an `EntitlementScope.Hinted` redemption - deliberately NOT at eligibility-resolution time, closing a real defect this slice's own audit found and fixed before it shipped: resolving eligible does not itself prove entitlement (a locally-valid envelope can still be server-rejected - revoked/expired/device-limit, the SAME `AUTHORIZATION_REJECTED` taxonomy, unchanged), so writing the constraint at resolution time would have let a server-REJECTED hinted attempt silently narrow Smart Connect away from a gateway this device was already genuinely, separately provisioned for. An `EntitlementScope.Unscoped` redemption (legacy credential, B67.4's own field-enrolled credential) never touches this field at any outcome. A PLURAL eligible set (multiple hinted, trusted, catalog-known gateways) is preserved as multiple candidates - `AutoGatewaySelector`/`TransportOrchestrator` remain the sole ranking/selection/execution authority, completely unmodified; this slice never ranks, never picks a winner, never touches transport selection or profile provisioning. Tests: `EntitlementGatewayEligibilityTest` (pure `filterEligibleEndpoints` cases - null passthrough, single/plural eligible, non-gateway entries untouched, empty list) and `MainViewModelSmartConnectEligibilityTest` (real end-to-end: unscoped/single-eligible/plural-eligible/server-rejected/manifest-still-authoritative/restart-equivalent-baseline, all against the real `autoGatewayCandidates()`/`combinedAutoAttempts()` MainViewModel surfaces `connectAuto()` itself uses) - 19 new tests, full `testDebugUnitTest` green except the one pre-existing `XrayXhttpRuntimeResolverTest` failure (unrelated - see B67.4's row for that same known failure). No production/infrastructure change; B67.4 remains disabled by default and untouched; no commercial entitlement/billing/subscription concept was introduced anywhere in this slice.
