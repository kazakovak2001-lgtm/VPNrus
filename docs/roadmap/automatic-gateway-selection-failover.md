## Column 3

**B17-2 update (2026-09-01)**: the B17 discovery fix below still had a gap - the executed `GatewayConfigSnapshot`'s `endpointHost`/`endpointPort` were still read from `ProductionGatewayCatalog` (`gateway.awg.endpointHost/endpointPort`), so a signed manifest could gate WHICH endpoints exist but a rotated host/port in that manifest would silently NOT reach the real AWG attempt. Fixed: `buildCandidates` now carries the EXACT `EndpointTransportBinding` each candidate was scored from (keyed alongside the catalog descriptor in an internal `Triple`), and `snapshotFor(gateway, binding, clientTunnelIp)` reads `endpointHost`/`endpointPort` from that `binding` - never from the catalog - for every candidate, AWG included. Server public key/gateway tunnel IP/obfuscation profile remain catalog-sourced (the manifest model doesn't carry them yet - a real, stated scope boundary). Proven by new tests with a manifest host deliberately DIFFERENT from the catalog's: `AutoGatewaySelectorTest`'s `configSnapshot host and port come from the manifest binding, not the catalog, even when they differ`, and `MainViewModelAutoGatewayTest`'s `auto connect to Germany dials the manifest host, not the catalog host` (asserts the REAL executed `AwgConfig.peer.endpointHost`/`endpointPort`, not just the candidate's snapshot). **Xray/TLS execution address audited and left honestly unmoved**: `VpnController.buildTransportConfig`'s XRAY_REALITY/TLS_TCP branches resolve the connect-time server address from the endpoint-scoped `XrayProfileRepository`/`XrayTlsProfileRepository` (real control-plane-activation-populated), never from `GatewayConfigSnapshot` - that snapshot is consumed only by the AWG path. An Xray/TLS candidate's snapshot is still built (every candidate carries one) and is now manifest-derived too for consistency, but changing it has no effect on where an Xray/TLS attempt actually connects; no Xray profile-ownership migration was performed to force this scope, per the task's own explicit instruction not to. **B17 update**: `AutoGatewaySelector.buildCandidates` no longer takes a raw `gateways: List<ProductionGatewayDescriptor>` - it takes `manifestEndpoints: List<EndpointDescriptor>`, which `MainViewModel.buildAutoGatewayCandidates()` sources from `manifestRepository?.trusted()?.endpoints` (the verified `TrustedManifestState`, empty/fail-closed when nothing verifies or `manifestRepository` isn't wired - never a fallback to the catalog). `ProductionGatewayCatalog` is now consulted only through a `gatewayFactsFor: (EndpointId) -> ProductionGatewayDescriptor?` compatibility lookup, invoked only for an endpoint id the manifest already named, to supply the AWG connection facts (server key, tunnel IP, obfuscation profile) that deliberately stay out of the public manifest. Local per-device provisioning (`ClientTunnelIdentityStore`, Xray/TLS profile availability) still gates which of the manifest's declared transports this device can actually use - a manifest naming an endpoint never implies local provisioning for it. Proven by new tests: an endpoint absent from the trusted manifest is never a candidate even though it exists in the catalog; no trusted manifest source yields zero candidates; both endpoints become candidates exactly when manifest + local provisioning both agree (`AutoGatewaySelectorTest`, `MainViewModelAutoGatewayTest`). The B16 candidate-identity/pinning/bounded-failover invariants below are otherwise completely unchanged - this is a discovery-source change only, not a rescoring or re-pinning change. Real, pure decision logic exists and is live-wired for real connect() attempts when `MainViewModel.gatewayAutoMode` is true (device-local, persisted, default `false`/Manual - every pre-B16 install stays Manual-only, byte-for-byte unaffected). `AutoGatewaySelector` (`smartconnect/AutoGatewaySelector.kt`) promotes the EXISTING `ReachabilityEngine`/`PathCandidateBuilder`/`PathScorer` pipeline (reused verbatim - see PathScorer's own "OBSERVATIONAL ONLY" note, now genuinely promoted for this one call site, not reimplemented) into a ranked `GatewayAttemptCandidate` list across every gateway this device is actually PROVISIONED for (`ClientTunnelIdentityStore`-backed, same readiness check the manual picker already uses - an unprovisioned gateway is never a candidate). `EndpointDescriptor`s for ranking come from `ProductionGatewayEndpoints`, built directly from `ProductionGatewayCatalog` - deliberately NOT the Signed Offline Bootstrap manifest (still only names "frankfurt"; extending it needs the offline manifest-signing key ceremony, explicitly out of scope for this slice). Candidate identity (`gatewayId`/`endpointId`/`transport`/`GatewayConfigSnapshot`) is resolved ONCE per candidate at ranking time and threaded verbatim into execution: `AutoGatewaySelector`'s `GatewayAttemptCandidate.configSnapshot` is carried through `TransportOrchestrator.resolve(..., gatewayConfigSnapshot = candidate.configSnapshot)` into `TransportOrchestrator.Resolution.Resolved.gatewayConfigSnapshot`, and `VpnController.connect()` pins it (`pendingConnectConfig`) for the ENTIRE attempt (including across a VPN-permission-prompt round-trip) - `doConnectAttempt()`/`gatewayStatus()` both resolve through this SAME pinned value (via the shared `GatewayConfigSnapshotValidator`, reused unchanged from `DefaultGatewayConfigurationRepository`) whenever it is set, and `gatewayConfigurationRepository`/`SelectedGatewayStore`/`ProductionGatewayCatalog`/`ClientTunnelIdentityStore` are NEVER re-consulted once a candidate is pinned - proven by `VpnControllerPinnedGatewayConfigTest` (mutating the repository/identity store after pinning, including across the permission-resume gap, provably cannot change what gets executed) and `MainViewModelAutoGatewayTest`. Manual gateway selection (`selectGateway()`) is completely unaffected (its `Resolution.Resolved` never carries a snapshot, so `doConnectAttempt`/`gatewayStatus()` fall through to `gatewayConfigurationRepository` exactly as every pre-B16 call site did), remains deterministic, and turns Auto back off when used. On a genuine terminal failure (`AutoGatewayFailoverPolicy` - the SAME enumerated HandshakeTimeout/BackendStartFailure categories `AwgXrayFailoverPolicy` already uses, never a generic catch-all), the existing `armFailoverWatch` collector advances to the next ranked candidate, bounded (`MAX_ATTEMPTS=4`, never retrying an already-attempted (gateway, transport) pair) and fails closed (`VpnError.NoCandidateAvailable`) once the ranked set is exhausted - never an unbounded loop, never a random pick. UNKNOWN reachability evidence is never treated as UNREACHABLE (PathScorer's own reachability tier already ranks UNKNOWN above DEGRADED/UNREACHABLE, unchanged); with no evidence at all, ties resolve deterministically via `PathScorer.rank`'s existing tiebreak (`SmartConnectDecisionEngine.PREFERRED_ORDER` then candidate id) - in practice AMNEZIA_WG on Germany before Stockholm, never random. **Failover model, stated precisely (consolidated review fix)**: `armFailoverWatch()` branches on whether the retained attempt carries an `autoContext` BEFORE it ever reaches the `AwgXrayFailoverPolicy` check - so during an Auto sequence, `AwgXrayFailoverPolicy` is NOT consulted at all; advancement follows the ONE globally-ranked gateway×transport candidate list instead (the preferred B16 model - a failed AWG candidate on one gateway can be followed by ANY higher-ranked remaining candidate, including that SAME gateway's own XRAY_REALITY/TLS_TCP or the OTHER gateway's AMNEZIA_WG, purely by rank, never a hardcoded "try Xray on this gateway first" chain). `AwgXrayFailoverPolicy`'s own intra-gateway AWG->Xray fallback continues to govern, completely unchanged, ONLY for Manual mode (`autoContext == null`) - it does not additionally run "within" an Auto sequence's current gateway the way an earlier draft of this row incorrectly claimed. Compact diagnostics (`MainViewModel.autoGatewayDiagnostics`/`.autoGatewayCandidates()`, surfaced in the debug diagnostics dialog) show the ranked candidate list, current/attempted candidates, last failure category, and the actual active gateway - never a secret/credential field.
