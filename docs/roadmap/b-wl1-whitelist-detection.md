## Column 3

Adds a new, closed, non-secret `TransportAttemptObservation` type (`smartconnect/TransportBehaviorEvidence.kt`: protocol TCP/UDP, connect/handshake stage outcomes, byte counts, `TrafficProgressOutcome`, `AttemptTermination` - opaque `destinationKey` only, never a host/IP/UUID/key) and a pure, deterministic `TransportBehaviorAnalyzer.assess()` that turns a bounded, network-scoped, FRESHNESS-CHECKED window of these into one `TransportBehaviorPattern` (`SUSTAINED_PROGRESS`/`EARLY_DROP`/`REPEATED_EARLY_DROP`/`REPEATED_EARLY_DROP_MULTI_DESTINATION`/`UDP_NO_RESPONSE_TCP_OK`/`ALL_CONNECT_FAILED`/`INSUFFICIENT`) plus a qualitative `RestrictionEvidenceQuality` (reused, not a second confidence model) - no byte-count threshold anywhere (a single byte and a million bytes hit the identical code path; see `TrafficProgressMonitorTest`'s own "no magic threshold" proof). `RestrictionClassifier` (the SAME, ONE classifier - `RestrictionEvidence.transportObservations` is a new, empty-by-default field) now also produces `POSSIBLE_EARLY_DROP`, `POSSIBLE_UDP_FILTERING`, and `POSSIBLE_FULL_SHUTDOWN` from this evidence, each requiring real corroboration (repetition and/or cross-destination spread, or - for UDP filtering - a working TCP flow on the same network) - never from one weak observation alone; a stall reset by the peer (RST) is never treated as an early drop; a stall on one destination while another sustains progress is `INSUFFICIENT`, never generalized. The existing `POSSIBLE_HARD_WHITELIST`/`POSSIBLE_UDP_OR_AWG_FILTERING`/`NO_NETWORK`/`NO_RESTRICTION_OBSERVED` rules and their required evidence are completely UNCHANGED - behavior evidence only adds new, additional routes to `POSSIBLE_HARD_WHITELIST` (an `ALL_CONNECT_FAILED` pattern plus the SAME existing diverse-reachability-failure evidence, never a shortcut from behavior alone) and to `NO_RESTRICTION_OBSERVED` (sustained progress). A new, network-scoped, IN-MEMORY-ONLY, bounded `TransportObservationStore` (`smartconnect/TransportObservationStore.kt`, capacity-bounded across all networks combined, never persisted, never mixes one network's evidence into another's read) holds recent observations. **Production wiring, stated precisely**: `VpnController`'s existing authoritative connect-outcome sites (the SAME ones `ConnectionOutcomeStore`/`PathHistoryStore` already write from) now ALSO write one `TransportAttemptObservation` per real attempt - but only CONNECT/HANDSHAKE-level success/failure (a fresh-handshake confirmation or its absence), never fabricated payload/stall/reset evidence this call site cannot see. This means `POSSIBLE_FULL_SHUTDOWN` and (for AMNEZIA_WG vs. a working TCP transport) `POSSIBLE_UDP_FILTERING` ARE reachable from real production evidence today, from every transport kind. **Live traffic-progress wiring (B-WL7, current pass)**: a real AmneziaWG session now ALSO samples its real `TransportStats.Counters` over a bounded post-handshake window (`VpnController.launchLiveProgressObservation`, reusing the same poll cadence `awaitFreshHandshake` already uses - no second polling loop, no second watchdog) and writes a richer observation carrying real `bytesReceived`/`progress` evidence, so `POSSIBLE_EARLY_DROP` and a payload-aware `POSSIBLE_UDP_FILTERING` ARE now reachable from real AmneziaWG production evidence. Every other transport kind's `stats()` still reports no real counters at all, so its observations stay connect/handshake-level only (honestly `NOT_OBSERVED` for payload/progress). A separate TCP failure-semantics fix (`TransportBehaviorAnalyzer.failedBeforePayload`) makes the live writer's genuine TCP failure shape (`connect=NOT_OBSERVED, handshake=FAILED` - this call site can only confirm a fresh handshake, never the lower-level socket-connect step in isolation) correctly reach `ALL_CONNECT_FAILED`, which the pre-existing `connect==FAILED`-only predicate could never reach from real evidence. No physical device test of any of this exists yet.
