## Notes

**2026-10-09 extension plan (target state, nothing below is implemented by this entry).** Per NACF, extend the existing decision pipeline - no new parallel "Capability Graph", "Policy Engine" or "Path Builder" layer. Responsibility map: link quality -> `PathScorer`; restriction / network risk -> `RestrictionClassifier` + B40 `RestrictionAssessment`; path composition -> B41 path synthesizer (`PathCandidateBuilder`); gateway selection and routing policy -> `RoutingDecisionEngine` + `GatewaySelectionMode`; execution -> `TransportOrchestrator`. Missing work: (1) feed measured RTT, loss, jitter and availability into `PathScorer` as a bounded tier (today only health/history/restriction/maturity tiers exist); (2) **verify, then extend** Auto to Direct `XRAY_XHTTP` and `HYSTERIA2` - `AutoGatewaySelector.buildCandidates` admits only AMNEZIA_WG / XRAY_REALITY / TLS_TCP / SHADOWSOCKS_2022 as Direct candidates (`else -> false`, re-checked 2026-10-09; see B-WL2); (3) Auto must keep honoring transport capability/eligibility, endpoint availability, network restriction evidence and prior-attempt history (existing gates - no bypass); (4) after a Wi-Fi <-> mobile change (`ReconnectManager` detects it today) re-evaluate the current path and keep it if it still passes the data-plane gate, reselecting transport/gateway only on evidence - no unconditional teardown; (5) decisions stay deterministic, attempts bounded, and existing failure semantics unchanged. `TransportScorer` remains non-decision-driving until (1) is designed. **2026-10-09 update:** PR #158 lets Auto learn from non-AWG Direct attempts (shared Xray session ids, path history per kind). An AWG session whose handshake succeeds but carries no data (RU `CONNECTED_NO_DATA`) now ends with `VpnError.DataPlaneNoTraffic` within ~30 s, is recorded as a failed path, and the existing failover watches move Auto to the next candidate / Manual(Auto transport) to Xray - see PROJECT_ARCHITECTURE "AWG dead-data-plane gate". Unit + MainViewModel-tested; healthy AWG held 45 s on the OPPO without teardown; Russia NOT MEASURED. `SmartConnectDecisionEngine` (Phase 2A) is real, pure, and unit-tested, and IS live-wired as of B8I1/B8I8 - `MainViewModel.connect()` calls `smartConnectDecision()` (via `SmartConnectCandidateSelector`) for every real MANUAL-gateway-mode attempt, and `AwgXrayFailoverPolicy` consults its outcome for AWG->Xray fallback. `SmartConnectDecisionEngine.decideAuto` (the single-gateway transport picker this powers) still picks by its own fixed `PREFERRED_ORDER` alone - its own `health` parameter is accepted but genuinely unused in the body, unchanged by B19 (Manual mode is deliberately kept simple/deterministic - see architecture principle 1 and B19's own precedence note below). **B19 (2026-09-01) clarification, not new scope**: this row previously read "gateway selection does not exist yet", which has been stale since B16 - `AutoGatewaySelector` (a SEPARATE, real decision authority for AUTOMATIC gateway mode specifically, see the dedicated row below) has reused this exact `PathScorer`/`ReachabilityEngine` pipeline since B16, and DOES let real health/reachability evidence reorder both gateway AND transport together for that mode. The two decision authorities are deliberately never merged (task requirement 1) - this row's own FOUNDATION status reflects `SmartConnectDecisionEngine`/Manual mode specifically, not automatic gateway selection's own (separately tracked) status.
