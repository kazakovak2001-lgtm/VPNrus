## Column 3

Type/verifier/issuer-tooling layer was DONE at B56-1..B56-4B1, and runtime wiring (`ActivationPackageImporter`/`ActivationPackageRedeemer`/`MainViewModel.importActivationPackage`) was DONE at B56-5 - both confirmed present and unchanged at this HEAD (superseding B67.1's now-stale "NOT wired" note, which predates B56-5). **This slice's actual contribution is an evidence-based audit, not new architecture:** it reads the real code (never assumes) to determine and document the ONE thing B67.1 correctly flagged as never explicitly decided - the `ActivationEnvelope` <-> legacy-credential relationship - plus adds the one previously-missing test proving the lifecycle-conflict authority rule end to end. **CONTRACT (determined from code, not chosen for elegance)**: `ActivationEnvelope.credential` (`activation/ActivationEnvelope.kt`) IS an `ActivationCredential` - the exact SAME `gateway/tools/activation_tokens.py`-issued bearer token the raw-credential UI flow already used pre-B56. `ActivationPackageRedeemer.activatePending` extracts `verified.envelope.credential.value` and hands it to the SAME `MainViewModel.activateDevice()` a typed credential uses (confirmed: no second `activationClient`, no second `ActivationResilienceCoordinator`, no second `ProvisioningClient` call). The gateway control-plane (`gateway/api/activations.py`) has ZERO awareness of `ActivationEnvelope`, issuer keys, or signatures - it authenticates purely via the legacy credential's own `decide_and_bind`/`max_devices`/`expires_at`/`status` record, exactly as before B56. So: **the legacy credential remains the ONE AND ONLY server-side authorization artifact, unconditionally live, never deprecated or compatibility-shimmed in any code path** - `ActivationEnvelope` is a CLIENT-SIDE-ONLY signed integrity/entitlement wrapper (issuer signature + validity window + local replay dedupe) around distributing that SAME credential offline, never a second/parallel authorization mechanism, never itself checked server-side. This is a determined fact about the current protocol, not an "owner decision" left open by B67.1 - what genuinely remains undecided is a forward-looking PRODUCT question (never chosen here, and not implemented): whether/when the legacy raw-credential manual-entry UI path is ever deprecated in favor of package-only distribution, and whether a future server-side envelope-verification path is ever built - both out of scope, neither assumed. **LIFECYCLE/AUTHORITY (audited, one new test)**: envelope-side checks (signature, issuer, `notBefore`/`expiresAt`, local replay) are evaluated FIRST and entirely offline, fail-closed, before the credential is ever read or any network call made (`ActivationPackageImporter.import`'s existing ordering, unchanged). Server-side rejection of the credential itself (revoked/expired/device-limit, `AUTHORIZATION_REJECTED` per B30's existing taxonomy) is authoritative over a locally-valid envelope: it was already provably terminal (never retried against another origin - B30) and never silently treated as success, but the ACTUAL `MainViewModel.activateDevice()` outcome-mapping code path (not a stand-in) had no direct test proving this for the package flow specifically - closed by 3 new tests in `MainViewModelActivationPackageAuthorityTest` (server rejection -> `ActivationFailed`, never locally marked redeemed so the same package can be re-attempted after the server-side condition is fixed, and the raw-credential and package-redeemed paths reaching the identical single `activationClient` call for the same credential/rejection - no second authorization engine, proven against real code, not mocks of the mapping itself). No B30/`ActivationResilienceCoordinator`/`ProvisioningClient` behavior was changed. **KNOWN, UNCHANGED-BY-THIS-SLICE GAP**: `ActivationEnvelope.bootstrapEndpointHints` is a signed schema field with ZERO runtime consumer anywhere in the codebase (grepped, confirmed) - inert data today, not wired into any endpoint-selection decision; documented here so it is never assumed active. `bootstrapCapabilityHint` is likewise carried but uninterpreted (by design, per B56-1). First redeemable production `ActivationEnvelope` still NOT issued (`PRODUCTION_ISSUER_OFFLINE_BACKUP_PENDING`, unchanged from B56-4B1/B67.1).
