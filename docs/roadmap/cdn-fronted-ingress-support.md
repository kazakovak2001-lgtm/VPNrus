## Notes

Threads B23's typed `IngressKind` (`DIRECT_IP`/`CDN_FRONTED`) - a real type since B23, never consumed anywhere until now - through real candidate construction, execution, and provisioning, so both ingress strategies coexist in one ranked relay fabric. `AutoGatewaySelector.RelayAttemptCandidate`/`RelayedExecutionPlan`/`RelayActivationRequest`/`IngressClientProfile` all gained an explicit, pinned `ingressKind` field, copied verbatim end to end - never re-derived, never inferred from host/provider. Server: `/v1/ingress-profile`'s response gained an optional `ingress_kind` field (`NOVA_INGRESS_KIND`, default `direct_ip`) which `IngressProfileProvisioner.provision` cross-checks against the pinned candidate and fails closed as `Mismatched` on disagreement - the exact "frontend/origin/backend confusion must fail closed" requirement. No kind-specific branch exists anywhere in execution (`RelayIngressResolverImpl`) or health/proof (`RelayReadinessStage`/`HttpRelayEndToEndProbe`/`VpnSessionHealth` - a CDN_FRONTED session reaches `RelayProtected` through the SAME end-to-end-proof-only gate) - deliberate: CDN_FRONTED is mechanically identical to DIRECT_IP from the client's own socket-level point of view, which is exactly why almost no new execution code was needed (task requirement D's "no second VPN service or second transport core", satisfied structurally). PR #41 review fix (same day): reachability/history is NOT left unchanged - `PathCandidate.Relayed.historyPathId` (`reachability/PathCandidate.kt`) now encodes `ingressKind` explicitly (`ingressId:ingressKind:transport->exitId:exitTransport`, was missing the kind component before this fix), so the SAME endpoint+transport reclassified between DIRECT_IP and CDN_FRONTED can never silently reuse the other kind's success/failure/cooldown evidence. No pre-B27 relay history exists on any real device, so this format change orphans nothing and needed no migration code - `PathHistoryStore.get()` already treats an unmatched key as "no evidence". Never hardcodes Yandex/VK/Beeline/Selectel/a bank/any real organization as trusted infrastructure, and never impersonates a third party's traffic identity - `CDN_FRONTED` names an OPERATOR-CONTROLLED CDN/origin architecture, never a spoof (architecture principle 3, re-affirmed not weakened). Tests: `PathCandidateBuilderTest`/`AutoGatewaySelectorTest` (DIRECT_IP default when undeclared, DIRECT_IP+CDN_FRONTED candidates coexist in one ranked list each keeping its own pinned kind AND a genuinely distinct historyPathId, the SAME endpoint+transport reclassified between kinds produces a different historyPathId, stale evidence recorded under one kind's key never influences PathScorer.score for the other kind's candidate at the identical endpoint+transport), `IngressClientProfileTest` (kind mismatch fails `matches()`, CDN_FRONTED JSON round-trip), `IngressProfileProvisionerTest` (server ingress_kind mismatch rejected as Mismatched and never persisted, a kind change forces `ensureFreshProfile` to refresh rather than reuse a stale profile), `MainViewModelRelayActivationTest` (activation retry preserves the exact pinned CDN_FRONTED candidate, never silently downgraded or re-ranked), `test_ingress_config.py`/`test_ingress_profile_endpoint.py` (NOVA_INGRESS_KIND validation, a CDN_FRONTED deployment echoes that kind in its response). Full Android suite (`compileDebugKotlin`/`testDebugUnitTest`/`assembleDebug`) and full gateway Python suite (327 tests, WSL native fs - one pre-existing, unrelated thread-timing flake in `test_activations.py`, reproduced on a clean `main` checkout with zero B27 changes, confirmed not a regression) both pass. **Not done this slice**: no real CDN-fronted ingress host exists to validate against; no product UI surfaces ingress kind (Home/LocationCard stay geography-only, matching this codebase's own production-vs-debug boundary); B26's DIRECT_IP-specific deployment/preflight/runbook tooling was not extended for a CDN-fronted rollout sequence (would need a real CDN account/configuration to design meaningfully).
