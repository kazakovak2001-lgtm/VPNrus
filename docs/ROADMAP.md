# Product roadmap - approved capabilities and current status

This document records the approved long-term capability set for the VPN
product. **It is documentation only.** Nothing in this file implements,
enables, or wires up any of the PLANNED/BLOCKED items - see each item's
status for what actually exists in the repository today, and see
`docs/AWG_GENERATION.md` / `gateway/README.md` and the later evidence below
for capabilities already exercised on real gateways and Android devices.

Rows whose notes grew past ~2000 characters keep their capability name and a
shortened status here; the full, unchanged row lives in `docs/roadmap/<name>.md`
behind its "full detail" link. Status changes go into both places; put long
evidence narrative only in the detail file.

## Status legend

| Status | Meaning |
|---|---|
| **IMPLEMENTED** | Real, working code exists and does what the name says. |
| **FOUNDATION** | Real, tested code exists (types, pure decision logic, an observer), but it is either not wired into the live product flow, or only covers part of the eventual capability. |
| **PLANNED** | Approved for the roadmap. No code exists yet. |
| **BLOCKED** | Approved, but cannot start/complete because of a stated external precondition. |
| **UNVERIFIED** | Not a feature - a *claim* about the running system (e.g. "no DNS leak") that has not yet been proven with real evidence, and must not be asserted as true until it is. |
| **UNIT-VERIFIED** | Behavior pinned by automated unit/JVM tests in this repository only - no running device, gateway, or network was involved. |
| **E2E-VERIFIED** | Exercised end-to-end on a real build against a real gateway; the row states the exact scope (build/commit, gateway). Says nothing about restricted networks. |
| **FIELD-VERIFIED** | Proven on a real restricted/target network (e.g. Russia) with recorded evidence. Nothing in this file currently carries this status. |
| **RESEARCH** | Investigation or evaluation only; no product commitment and no production code. |
| **DEFERRED** | Deliberately outside the current execution focus; the row states what would unblock it. |

A capability's status here is not a promise about when it ships - it is a
truthful snapshot, updated as each gate (B6, B8B, B9, B10, and beyond)
actually lands.

## Mandatory runtime sequence (unchanged)

```
B6  - real VPS provisioning
B8B - public AWG handshake
B9  - full-tunnel external IP validation
B10 - DNS / IPv4 / IPv6 leak validation
```

The original sequencing rule deferred new transports until B10 completed on
a real VPS. XRay/REALITY was the first historical exception: its full
client and gateway runtime was built and live-wired ahead of B10, and its
AWG->Xray automatic failover has since been **verified** end-to-end on a
real VPS (see the XRay / VLESS REALITY fallback row below). Phase 2A
provided architecture foundation ahead of that sequence; the later B10
completion removed this process gate for subsequent transport work.

**As of B10-1 (2026-08-30), the B6->B8B->B9->B10 sequence above is
itself complete** - see the "Current verification status" table below:
public AWG handshake, public VPS NAT behavior, external IP change, and
DNS/IPv4/IPv6 leak protection are all now VERIFIED with real physical-
device evidence (B6, real VPS provisioning, has been implicitly true
throughout this document's B8I/B8K/B8L/B8M/B8N history - the gateway at
`152.70.43.1` this evidence was gathered against is that same real VPS).
This means the sequencing GATE itself - not merely an exception granted
to one transport - no longer blocks QUIC/TLS/TCP-fallback/Shadowsocks
runtime work on process grounds; any decision to start one is now a
scope/priority choice, not a blocked one. `Real restrictive-network/

**UNVERIFIED and separate** - B10's leak validation says nothing about
behavior on an actually-restrictive network, and must not be conflated
with it.

## Architecture principles this roadmap commits to

1. **Routing decision and transport selection stay separate.** "Should this
   traffic use the VPN at all" (`RoutingDecisionEngine`) is never the same
   question as "which transport carries it" (`SmartConnectDecisionEngine`).
   Do not merge these two concerns as the roadmap items below are built.

2. **Target Smart Connect pipeline:**

   ```
   NetworkProfiler -> RestrictionClassifier -> RoutingDecisionEngine
   ReachabilityEngine -> PathCandidateBuilder -> PathScorer
     -> AutoGatewaySelector (automatic gateway mode)
     -> TransportOrchestrator -> VpnController
   ```

   The B11 observational-only description was a historical baseline,
   superseded by B16/B19: `AutoGatewaySelector` now consumes the existing
   reachability/scoring fabric in automatic mode, selects real gateway and
   transport candidates, and has physical Android gateway-selection evidence.
   Manual mode retains its separate `SmartConnectDecisionEngine` transport
   picker. `RoutingDecisionEngine` is the live DIRECT-vs-VPN route authority
   (B18); it does not choose a gateway. Restriction evidence is consumed
   conservatively by routing and automatic candidate ranking (B18/B28),
   without country or provider-name rules. The physical B16 pass excluded an
   unprovisioned gateway; same-request mid-connect timeout failover remains
   unit-tested, as documented in its row below.

3. **Distinct failure conditions.** A connection attempt that fails must be
   attributable to one of (at minimum):

   - `PROTOCOL_BLOCKED` - the transport protocol itself appears filtered.
   - `GATEWAY_UNREACHABLE` - this specific gateway/endpoint is down or
     unreachable, independent of protocol.
   - `NETWORK_UNAVAILABLE` - the device has no usable network at all
     (already modeled: `NetworkProfile.isUsable`,
     `TransportSelectionDecision.NetworkUnavailable`).
   - `HARD_WHITELIST` - the network appears to only permit a fixed set of
     allowlisted destinations (see Hard Whitelist Detection below).

   These must never be collapsed into one generic "connection failed"
   state - each implies a different remediation (retry, switch gateway,
   switch transport, or something structurally different for hard
   whitelists).

4. **Hard Whitelist Detection must never impersonate a real third-party
   service.** Detecting that a network only allows traffic to a fixed
   allowlist (e.g. a bank, Yandex, VK) must not be implemented by
   pretending to *be* one of those services, spoofing their traffic
   signature, or otherwise misrepresenting the client as that service.
   Detection is passive/observational only.

5. **Adaptive Direct Routing** means genuine `DIRECT` routing (the
   underlying network, unmodified) for explicitly allowed/local traffic,
   and VPN routing for everything else classified as needing protection.
   It uses the existing `RoutingDecisionEngine` / `ClientRoutingPolicy`
   model. B18 wired the real `RestrictionClassifier` conservatively into
   route decisions, and later physical validation promoted Adaptive Direct
   Routing to IMPLEMENTED (see its row). This is not a new routing primitive.

6. **Transport selection uses capability/health scoring, not hardcoded
   if/else.** `TransportCapabilities` and `TransportHealth` (Phase 2A,
   FOUNDATION) exist for exactly this reason: as more transports become
   real, `SmartConnectDecisionEngine` must be extended to score across
   these typed fields, never to grow a chain of per-protocol conditionals.

7. **Public gateway infrastructure must span multiple providers/ASNs.**
   Relying on a single provider (e.g. Hetzner alone) for all gateways is
   not the target architecture - see Gateway Pool / multi-provider gateway
   infrastructure below. A real, physically-verified production VPS has
   existed since B10-1/B8O2 (2026-08-30), so this is no longer BLOCKED on
   "zero provisioned gateways" - it is now a scope/priority choice (PLANNED),
   the same reconciliation already applied to the B6->B10 sequencing gate
   above. Germany/Oracle and Stockholm/AWS are both deployed, have distinct
   provider/ASN facts in `EndpointDescriptor`, and have physical AWG,
   REALITY and TLS/TCP evidence (B13-B16). A durable, diversified product
   pool and CDN/control-plane diversity remain future work.

8. **Signed Offline Bootstrap** must let the client retain a
   cryptographically verified last-known-good gateway/control
   configuration for use when the primary control API is unreachable - not
   an unauthenticated cached blob.

9. **Private Gateway Mode is a first-class capability, not a fallback.**
   A user may connect through the managed gateway network *or* their own
   compatible VPS running the same pinned AmneziaWG gateway
   (`gateway/provision.sh`) - both are supported product modes.

10. **Privacy claims stay truthful.** Nothing in this product may claim
    "untraceable," a guaranteed censorship bypass, or a guaranteed
    hard-whitelist bypass. Every capability below is described by what it
    actually does, not by an outcome no software can promise.

## Current execution order (2026-10-09, driven by the first RU field evidence)

Documentation-only priority order; it changes no row's status. It follows
the first Russia evidence under B54 (one home Wi-Fi, one tester,
2026-10-07/08 - see "Current verification status") and a review of an
external technology-monitoring summary. That summary was treated as input,
not as evidence: where it disagreed with this repository, the repository
won (see "Discrepancies found" below).

Evidence levels used in this section: **observed** = measured once in the
named environment; **hypothesis** = plausible, not measured; **confirmed** =
measured repeatedly or across environments. Nothing here is FIELD-VERIFIED.

1. **Non-`.pp.ua` domain - owner decision, then validation.** See the P0
   row "Non-`.pp.ua` Client-Facing Domain".
2. **B54 Russia field test** - RU home Wi-Fi and RU mobile network kept
   separate, plus a confirmed-whitelist network if one becomes available.
   See "RU field validation plan (B54)" below.
3. **Data-plane proof and leak checks for every production-supported
   transport** - B-WL7 acceptance criteria below, plus the per-transport
   Android leak matrix (P1 row).
4. **Independent control-plane origin and unambiguous bootstrap
   diagnostics** - the "Alternative Control Routing" P0 row.
5. **AWG 3.1 client benchmark and the Android leak matrix** - P1 rows.
6. **Smart Connect** - link quality in `PathScorer`, Auto coverage of the
   supported paths, re-evaluation after a network change. See the Smart
   Connect row's 2026-10-09 extension plan.
7. **Fingerprints, general multi-hop and further research** - only after
   gates 1-6. Multi-hop, MASQUE, post-quantum, RAM-only, traffic-analysis
   defense and protocol imitation stay at their existing PLANNED/RESEARCH
   status; this order moves none of them into P0/P1. No new transport is
   added for its own sake (see the Shadowsocks and QUIC rows' 2026-10-09
   notes).

### Discrepancies found while reconciling the external summary (2026-10-09)

- The summary named the missing bootstrap error states
  `BOOTSTRAP_UNREACHABLE` / `VPN_TRANSPORT_FAILED`. Neither exists in code.
  The existing closed vocabulary is B30's `CONTROL_PLANE_*` family
  (`CONTROL_PLANE_DNS_FAILURE` ... `CONTROL_PLANE_ORIGINS_EXHAUSTED`) plus
  `MANIFEST_UNAVAILABLE` and the transport/data-plane reasons in
  `DiagnosticFailureReason`. The requirement is recorded against that
  existing vocabulary - no second enum.
- "Data-plane proof only for AWG" is only partly true. What is AWG-only is
  the B-WL7 post-connect traffic-progress gate (`VpnController`'s single
  caller is the AmneziaWG success branch). Xray REALITY/TLS already have a
  connect-time in-tunnel confirmation (B33 `confirmRemoteConnectivity`) and
  relays have the post-Connected relay-health watchdog. Hysteria2 had no
  in-tunnel confirmation; added 2026-10-09 (`Hysteria2TunnelProbe`, see the
  B-WL7 acceptance table).
- B57 is the control-plane edge behind Cloudflare; B35 is the CDN/XHTTP
  data-plane ingress. The summary conflated them; this roadmap keeps them
  separate.
- B67.7 is already IMPLEMENTED (narrow scope), not a pending step.
- Network change: `ReconnectManager` already detects Wi-Fi <-> mobile
  handover; what is missing is path re-evaluation after it (no row existed).

**Known limitation M1 (Direct Xray gate).** The Direct Xray post-connect gate (`VpnController.launchLiveProgressObservation`, `TrafficProgressMonitor.evaluate`) sees only the `:xray` core's VLESS-outbound byte totals, which carry no handshake or TCP ACK bytes. If uplink grows while downlink stays flat for the stall window (65 s for Direct Xray since P2, previously 20 s) and that silence starts within the first 10 s of the 75 s observation window (nominal sample times) after the B33-confirmed Connected, the verdict is `NO_PAYLOAD` / `STALLED_AFTER_INITIAL_PAYLOAD` and `failDeadDataPlane` ends the session with `DataPlaneNoTraffic` (Auto advances; a Manual pin ends in Error). A healthy session whose only traffic is an upload awaiting a delayed reply produces the same counter pattern as a dead exit, so it is ended the same way. Status: (1) confirmed behavior of the decision logic - the unit test "Xray uplink with no downlink ends the session with DataPlaneNoTraffic" exercises this input; (2) real-world frequency unknown; (3) not yet reproduced as a false teardown on a device - the REALITY 11/11 and TLS 1/1 device runs did not target this case. **Independent-egress probe (F1, IMPLEMENTED IN REPO, UNIT-VERIFIED; device/log-verified only through a debug hook on `cb22eee`, 2026-10-16):** before acting on NO_PAYLOAD / STALLED the gate asks `VpnTransport.probeIndependentEgress()` ONCE per check (caller bound 10 s; `:xray` bound 6 s): one `https://<other catalog gateway>/v1/tunnel-probe` round trip through THIS session's core (pinned wrapper `measureInstDelay`: HTTP 200/204 only, Go default TLS verification against the IP certificate, body read, redirects followed). REACHED proves only that this probe endpoint answered through this exit - never that arbitrary destinations work. REACHED re-reads the counters (probe bytes are not user progress) and extends the window ONCE by one 65 s stall window: a stall seen after it still ends the session; silence in BOTH directions afterwards ends `IDLE` and, like every `IDLE`, leaves the session Protected (policy, not a fault: an idle tunnel and a tunnel whose user destination is dead look the same). NOT_REACHED, UNAVAILABLE, a timeout or an exception keep the teardown. The gate is one-shot: nothing re-checks the session after its window. Physical evidence (debug hook, OPPO, 2026-10-16): Frankfurt->Stockholm REACHED 341 ms, Stockholm->Frankfurt REACHED 453 ms, and both targets' nginx access logs show the request from the FIRST gateway's public address. Not exercised: a real dead-egress case (needs an owner-approved server-side fault). The `dataPlaneChecks` report items now also carry `generation`, `egressProbe` (`outcome` REACHED / NOT_REACHED / UNAVAILABLE / CALLER_TIMEOUT / EXCEPTION, `durationMs`, `verdictBefore`, `rebaselined`) and `action` (PRESERVED / TORN_DOWN / STALE_IGNORED); NOT_REACHED also covers failures the `:xray` side folds into it (TLS, HTTP status, its own bounds). **P2 (mitigation, IMPLEMENTED IN REPO, UNIT-VERIFIED; not field-tested on any Russian network):** `TrafficProgressPolicy.forTransport(transport.kind)` gives XRAY_REALITY / TLS_TCP / XRAY_XHTTP a 65 s stall window (was 20 s); AWG and every other kind keep 20 s; the verification window stays 10 s for all. It reduces the risk of a premature teardown of a healthy session awaiting a delayed reply; it is not evidence of a healthy data plane, it delays detection of a really dead Direct Xray session by up to 45 s, and it does not remove the M1 ambiguity (a silence longer than 65 s is still ended the same way). **Diagnostics (repo only, UNIT-VERIFIED; not yet seen in a device log):** the `B-WL7 data-plane check` logcat line keeps its existing prefix and now also prints `stallWindowMs`, `verificationWindowMs`, `silentForMs`, `polls`, `maxPolls` and `end` (`DECISIVE_VERDICT` / `WINDOW_EXHAUSTED` / `COUNTERS_UNSUPPORTED`), so a device run shows which stall policy was actually applied. `silentForMs` and sample times are NOMINAL (poll index x 500 ms), not measured device time; real elapsed time is longer by the counter-read latency, so field timing must be read from logcat timestamps. **Report section (2026-10-16, device-verified on one OPPO / Android 14 for REALITY and AWG; not tested on any Russian network):** the field-test JSON may now carry an optional `dataPlaneChecks` section (in-memory, last 10 checks, independent of logcat rotation) with per-check `checkId`, `status` (`RUNNING` / `COMPLETED` / `CANCELLED` / `ABORTED`), transport, verdict, `stallWindowMs`, `verificationWindowMs`, `samples`, `polls`, `maxPolls` and `end`; `silentForMs` there is likewise NOMINAL, not a wall-clock measurement.

**Layer 3a - tunnel configuration check (2026-10-27, IMPLEMENTED IN REPO, UNIT-VERIFIED, observational only; not device-verified on a Connected session):** once per Connected session on every transport, `VpnController` reads the system's view of this app's VPN network (`AndroidTunnelLinkReader` -> `ConnectivityManager.getLinkProperties`, bounded 3 reads 1 s apart) and `TunnelProtectionCheck` evaluates it: public IPv4 covered by tunnel routes (FULL_VPN and ADAPTIVE both pass), DNS servers = `VpnDnsPolicy` and inside the tunnel, IPv6 `CAPTURED` (::/0, AWG) or `BLOCKED` (no IPv6 on the tunnel, Xray - Android drops the family) vs `PARTIAL`. Result `VERIFIED` / `LEAK_SUSPECTED` (+ findings) / `NOT_VERIFIABLE`, kept in `TunnelProtectionLog` and in the field report as `protectionChecks`. It sends no traffic and contacts no third party. It never ends a session or changes Protected - teardown on `LEAK_SUSPECTED` is a later decision after device evidence. It checks configuration, not egress: **3b (egress IP = chosen gateway) is still open** and needs either an own-gateway echo endpoint (server change) or a third-party lookup.

No transport is claimed to satisfy all four layers today.
